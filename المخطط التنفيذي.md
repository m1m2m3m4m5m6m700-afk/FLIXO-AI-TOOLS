## 1. الخلاصة التنفيذية

المستودع يحتوي عدة وثائق تخطيطية، لكن مضمونها يمكن توحيده إلى مسار واحد:

**Scope → Public Agent Boundary → Model Admission → Model Failover → Canonical ToolPlan → Validation → Local Executor → Independent Verifier → Recovery/Fallback → Observability → Red-Team → Browser Acceptance → Exact-SHA CI → Human Review/Promotion**

لا ينبغي إنشاء خطة تنفيذ موازية لكل محور. الوثائق المتخصصة تبقى مراجع تفصيلية، وهذا الملف يربطها بحالة واحدة.

## 4. خطة التنفيذ الموحدة من الآن

### المرحلة 0 — تثبيت الحقيقة
1. إعادة قراءة Exact SHA الحالي.
2. عدم استخدام أي evidence من SHA أقدم.
3. قراءة PR #889 وحالة required checks.
4. تثبيت قائمة failures فقط من evidence الحالي.

### المرحلة 1 — إغلاق عقود الوكيل
1. public agent = FLIXO_AGENT.
2. رفض direct specialist selection/injection.
3. عدم تسريب specialist identity إلى public response contract.
4. تشغيل gateway/orchestrator tests.

### المرحلة 2 — إغلاق model governance/runtime
1. Model Fabric هو المصدر الفعلي للاختيار.
2. admission = PASS + ACTIVE + task-compatible.
3. UNKNOWN/REVIEW/BLOCKED/QUARANTINED = fail closed.
4. لا raw File/Blob bytes إلى planning provider.
5. deterministic fallback عند غياب candidate.

### المرحلة 3 — إغلاق resilience
1. candidate A → B → C.
2. bounded attempts.
3. circuit breaker.
4. no retry loop.
5. no automatic model promotion.
6. نفس ToolPlan contract بعد fallback.

### المرحلة 4 — إغلاق ToolPlan
1. structural validation.
2. parameter/value validation.
3. semantic intent validation.
4. canonical capability registry.
5. non-executable capability = reject.
6. rejected plan لا يصل إلى executor.

### المرحلة 5 — التنفيذ والتحقق
1. Executor ينفذ فقط canonical capability.
2. Verifier مستقل.
3. executor success ≠ task success.
4. verifier failure = failure/recovery/manual fallback.

### المرحلة 6 — privacy + observability + idempotency
1. browser-local file execution.
2. network boundary proof.
3. trace allowlist.
4. لا secrets/raw bytes.
5. stable execution identity للعمليات state-changing.

### المرحلة 7 — Red-Team
تشغيل المصفوفة:
- specialist injection
- unregistered model
- bad artifact hash
- license quarantine
- provider outage
- circuit open
- all-provider failure
- malformed plan
- invalid values
- semantic mismatch
- non-executable capability
- verifier failure
- network bytes violation
- duplicate state-changing request
- memory contamination
- stale SHA evidence

### المرحلة 8 — Functional + Browser
1. English intents.
2. Arabic intents.
3. compound requests.
4. ambiguity/fail-closed.
5. AI guided workflow.
6. manual standalone workflow.
7. browser execution/result verification.

### المرحلة 9 — Exact-SHA Certification
لا PASS إلا إذا:
- كل required checks على نفس SHA PASS؛
- لا skipped/cancelled required checks؛
- browser evidence مربوط بنفس release candidate؛
- evidence SHA موحد؛
- PR/change-control rules مستوفاة؛
- لا claims قانونية تتجاوز evidence.

## 6. أسئلة مطلوبة من الوكلاء والمراجعين

على كل وكيل مراجعة هذا الملف والوثائق المشار إليها، ثم تقديم:

1. **Contradictions:** أي تعارض بين الخطط أو العقود.
2. **Duplicate Systems:** أي registry/authority/executor/verifier مكرر.
3. **Execution Gaps:** ما هو موثق لكنه غير مربوط فعلياً بالـruntime.
4. **Test Gaps:** ما هو غير مثبت باختبار.
5. **Security Gaps:** أي bypass أو privilege escalation محتمل.
6. **License/Provenance Gaps:** أي model evidence ناقص.
7. **MVP Scope Gaps:** أي capability خارج/داخل النطاق بلا دليل.
8. **Browser/Privacy Gaps:** أي احتمال لعبور file bytes للشبكة.
9. **Certification Gaps:** ما يمنع Exact-SHA certification.
10. **Recommended Next Action:** إجراء واحد محدد وقابل للتنفيذ، مع الملف/الاختبار الذي يجب تغييره.

صيغة الرد المطلوبة من الوكلاء:

`FINDING-ID | SEVERITY | FILE | EVIDENCE | IMPACT | PROPOSED ACTION`

لا يُطلب من الوكلاء إصدار شهادة أو دمج تغييرات. دورهم advisory/review فقط.

- `docs/FLIXO-MVP-EXECUTION-AND-CERTIFICATION-PLAN.md` = خطة إغلاق MVP.
