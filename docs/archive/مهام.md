# خطة تنفيذ نظام وكيل FLIXO — Execution Work Packages

## الهدف
تحويل FLIXO إلى وكيل تفاعلي احترافي عالي الاعتمادية، قابل للتوسع إلى 40 Engine و1000+ Capability دون تضخم Agent Core، مع تنفيذ محلي عندما يكون ممكنًا، تخطيط قابل للتحقق، تأكيد صريح، تنفيذ متدرج، تحقق من النتائج، تعافٍ وإعادة تخطيط بحدود، وذاكرة آمنة للسياق، مع رفع الجاهزية التنافسية في البحث إلى هدف 95/100.

## مبدأ التسريع
بدل عشرات المهام الصغيرة المتداخلة، تُنفذ الأعمال في **حزم كبيرة مترابطة**. كل حزمة تُغلق جميع العقود التابعة لها وتنتج دليلًا قابلًا للتحقق قبل الانتقال للحزمة التالية. لا نبني صفحات أو أنظمة لا ترتبط مباشرة بالمنتج أو بقياس قابل للتحقق.

```text
WP0 Trust Baseline
      ↓
WP1 Registry + 40 Engines
      ↓
WP2 Security + Observability + Error Intelligence
      ↓
WP3 Understand + Ask + Plan + Confirm
      ↓
WP4 Execute + Verify + Recover + Memory
      ↓
WP5 Contract/E2E/Adversarial Testing
      ↓
WP6 Performance + Local-first + AI enhancement
      ↓
WP7 SEO 95 + i18n + UX + Release
```

## دورة الوكيل النهائية

```text
REQUEST
  ↓
UNDERSTAND
  ↓
MISSING INFO?
  ├─ YES → ASK → UNDERSTAND
  └─ NO
       ↓
PLAN → PLAN GUARD → AWAITING_CONFIRMATION
       ↓                    ├─ CANCEL → CANCELLED
   CONFIRM                  └─ CONFIRM → EXECUTING
                                  ↓
                           STEP → VERIFY
                                  ↓
                           NEXT / COMPLETE
                                  ↓
                              RECOVER
                                  ↓
                              REPLAN
                                  ↓
                       RECONFIRM* / EXECUTE
```

`*` إعادة التأكيد إلزامية إذا غيّرت إعادة التخطيط قرارًا مؤثرًا للمستخدم.

## قواعد غير قابلة للتجاوز
- `main` هو مصدر الحقيقة للإنتاج.
- لا تنفيذ قبل confirmation صريح عندما تتطلب المهمة تأكيدًا.
- Planner لا يرى إلا الأدوات الموجودة في Registry والقابلة للتنفيذ.
- لا تخمين للمعاملات المؤثرة.
- نجاح استدعاء الأداة لا يساوي نجاح المهمة؛ يجب التحقق من الناتج.
- لا منطق خاص بكل أداة داخل Agent/Planner/Executor/Verifier.
- ممنوع `if tool === "..."` لتوسيع النظام.
- إضافة Engine/Capability صحيحة يجب ألا تتطلب تعديل Agent Core.
- الذاكرة لا تمنح صلاحيات ولا تتجاوز Security أو Registry.
- Recovery/Replan محدودان ومقيدان بالعقود.
- لا `GREEN` دون دليل مرتبط بالـSHA نفسه.
- لا استرجاع تاريخي عشوائي؛ التصنيف: `RESTORE / MERGE / ADAPT / KEEP-LEGACY / DO-NOT-RESTORE`.
- لا SEO score يُعلن دون Evidence من الاختبارات والصفحات المنشورة والقياسات الفعلية.
- لا إنشاء 1000 صفحة رقيقة؛ الـ1000 هي Capabilities داخل Engines، وليست 1000 صفحات SEO.

# P0 — MASTER ENGINEERING ROADMAP: الوصول إلى 100/100
**الحالة: ACTIVE — أولوية تنفيذ رقم 1**

## الهدف التنفيذي
تحويل FLIXO من حالة إصلاحات متفرقة إلى مسار هندسي مغلق الحلقة يصل إلى **100/100 تشغيليًا** فقط عندما تثبت الاختبارات والعقود والأدلة أن النظام مستقر وآمن وقابل للصيانة والتوسع. الرقم هنا **هدف داخلي للجاهزية** وليس ادعاءً يُعلن قبل اكتمال البوابات.

## البرومبت التنفيذي الرئيسي

```text
أنت الوكيل التنفيذي الرئيسي لـ FLIXO-AI-TOOLS.

المهمة الوحيدة ذات الأولوية:
رفع الجاهزية الهندسية للمستودع إلى 100/100 عبر إصلاح الجذور، وليس عبر إخفاء الأعراض أو تخفيف الاختبارات.

المستودع:
m1m2m3m4m5m6m700-afk/FLIXO-AI-TOOLS

القاعدة الأساسية:
لا تعتبر المهمة منتهية بسبب نجاح خطوة منفردة، أو Build، أو Vercel، أو PR جزئي.
المهمة لا تُغلق إلا عند وجود Exact-SHA Evidence + Canonical CI GREEN + عدم وجود RED/failed checks ذات صلة.

==================================================
1. DISCOVER — اكتشاف كامل قبل الإصلاح
==================================================
- افحص الحالة الفعلية لـ main، الفروع، PRs، workflows، jobs، artifacts، logs، tests، contracts، diagnostics وtask state.
- حدد كل RED/failed/timed-out/error state الحالي.
- اربط كل فشل بالـworkflow/job/step/SHA والسبب المحتمل.
- لا تعتمد على آخر خطأ فقط؛ افحص السجل التاريخي واكتشف التكرار والسباقات والـregressions.
- صنف كل مشكلة إلى:
  validation / type / lint / build / runtime / browser / SSR-hydration / routing / dependency / security / infrastructure / orchestration / observability / data-contract / SEO / performance.

==================================================
2. ROOT-CAUSE FIRST — إصلاح الجذر
==================================================
- لكل خطأ، أنشئ فرضية قابلة للدحض ومبنية على Evidence.
- إذا كانت الأدلة غير كافية، حسّن التشخيص أولًا بدل تكرار الإصلاح نفسه.
- ممنوع PROPOSAL_ONLY كبديل دائم للإصلاح عندما يمكن إضافة instrumentation أو اختبار يرفع ثقة RCA.
- ممنوع إصلاح عرضي يخفي الخطأ دون إثبات أن السبب الجذري زال.
- أعطِ أولوية خاصة لأخطاء WebKit/browser rendering وSSR/CSR hydration وTanStack Router/routing إذا ظهرت في CI.
- اربط RCA بالـexact target SHA وبالـlogs/artifacts ذات الصلة.

==================================================
3. REPAIR — إصلاح برمجي احترافي
==================================================
- أصلح الكود والعقود والـworkflow عند الحاجة، بأقل تغيير آمن يزيل الجذر.
- لا تعطل tests أو security gates أو type checks أو build لإجبار CI على GREEN.
- لا تضف استثناءات خاصة بأداة واحدة إذا كان العقد العام قادرًا على حل المشكلة.
- حافظ على Registry كـSingle Source of Truth.
- حافظ على metadata-driven Agent/Planner/Executor/Verifier.
- أي إصلاح يجب أن يكون قابلًا للتوسع ولا يضيف technical debt غير ضروري.

==================================================
4. VERIFY — تحقق متعدد المستويات
==================================================
بعد كل إصلاح:
1) syntax/typecheck
2) lint/static checks
3) targeted regression test
4) integration/contract test
5) browser/E2E عند انطباقه
6) build
7) canonical CI على نفس SHA

- استخدم Playwright traces/screenshots عند فشل browser tests.
- استخدم React onRecoverableError/trace IDs عندما يكون ذلك مناسبًا لتحديد hydration/runtime failures.
- لا تعتبر نجاح الاختبار المحلي كافيًا إذا كانت canonical CI ما زالت حمراء.

==================================================
5. SELF-HEALING LOOP — دورة إصلاح مغلقة
==================================================
```text
FAILURE
  ↓
CAPTURE EVIDENCE
  ↓
CLASSIFY
  ↓
ROOT-CAUSE HYPOTHESIS
  ↓
BOUNDED REPAIR
  ↓
TARGETED VERIFY
  ↓
CANONICAL CI
  ↓
GREEN? ── YES → LEARN + CLOSE
   │
   NO
   ↓
NEW EVIDENCE / NEW STRATEGY
   ↓
NEXT BOUNDED CYCLE
```

- كل دورة يجب أن تضيف Evidence أو Diagnostic Change حقيقيًا.
- لا تكرار لنفس strategy بلا تغيير معلوماتي.
- عند الوصول إلى حالة Intractable، أوقف التكرار واطلب Teaching Packet وفق `SUPERVISING-REPAIR-TEACHING-v1`.
- لا تستخدم escalation كوسيلة لتجاوز verification.
- لا تُعلن نجاحًا للحالة Intractable حتى ينتج Strategy جديد موثق `verified-repair` على نفس SHA ويمر canonical CI.

==================================================
6. SECURITY — Fail Closed
==================================================
- لا صلاحيات غير ضرورية.
- لا تنفيذ مباشر غير محكوم على main.
- الإصلاحات الآلية تمر عبر repair branch/isolated change ثم canonical CI.
- auto-merge مسموح فقط بعد GREEN وجميع gates المطلوبة.
- لا secrets في logs/artifacts.
- لا تعطيل CodeQL/AST/security/audit gates لتجاوز فشل.
- لا تعديل في verification logic بغرض تحويل failure إلى success.

==================================================
7. ERROR MEMORY — التعلم الحقيقي
==================================================
لكل failure مهم احفظ:
- fingerprint
- exact SHA
- workflow/job/step
- root cause
- evidence
- attempted strategies
- rejected approaches
- successful repair
- verification evidence
- canonical CI result

- استخدم التاريخ لمنع تكرار الحلول الفاشلة.
- افصل بين الحالات المختلفة بالـfingerprint.
- لا تجعل الذاكرة مصدر صلاحيات أو مصدر حقيقة بديلًا.
- عند escalation يجب أن تتضمن Teaching Packet:
  fingerprint
  newHypothesis
  diagnosticChange
  repairStrategy
  verificationPlan
  doNotRepeat
  exitCriteria

==================================================
8. ARCHITECTURE — لا تضخم Agent Core
==================================================
- Registry → Planner → Executor → Verifier يجب أن تبقى metadata-driven.
- إضافة Engine/Capability جديدة يجب ألا تتطلب تعديل Agent Core.
- امنع duplicate definitions وmanual lists وtool-specific branches.
- حافظ على contracts typed وقابلة للاختبار.
- اجعل Auto-Discovery وvalidation وdeterministic ordering قابلة للتحقق آليًا.

==================================================
9. ROUTING / SSR / BROWSER — عقد عدم الانحراف
==================================================
- اجعل file-based TanStack Router هو مصدر الحقيقة إذا كان هو architecture المعتمد.
- امنع تضارب manual router مع generated route tree.
- افحص SSR/CSR parity وhydration deterministically.
- اختبر Chromium/WebKit عند الحاجة ولا تعتبر Chromium وحده إثباتًا كافيًا لمشكلة browser-specific.
- اجعل browser failures قابلة لإعادة الإنتاج عبر fixture أو trace عند الإمكان.

==================================================
10. PERFORMANCE — السرعة دون إضعاف الثقة
==================================================
- قس الزمن قبل وبعد أي تحسين.
- استخدم dependency caching/artifact reuse/build reuse عندما يثبت فائدته.
- لا تحذف التغطية القانونية من main.
- استخدم Test Impact Analysis في PR فقط مع fallback إلى full suite عند عدم اليقين.
- اجعل browser sharding متوازنًا بالزمن لا بعدد الملفات فقط.
- اجعل traces/videos عند الفشل افتراضيًا عندما لا توجد حاجة دائمة لها.

==================================================
11. PRODUCT / SEO / i18n — الجودة الفعلية
==================================================
- لا تنشئ صفحات رقيقة.
- كل Engine منشور يجب أن يملك وظيفة حقيقية وmetadata ومحتوى مفيدًا وأدلة مناسبة.
- canonical/hreflang/sitemap/robots يجب أن تتوافق مع الصفحات الفعلية.
- 20 لغة × 22 أداة أو أي توسع لاحق يجب أن يعتمد نفس contract لا نسخًا يدوية.
- لا hardcoded UI strings في locale غير الصحيح.
- لا تعلن SEO score دون Evidence فعلي.

==================================================
12. DEFINITION OF 100/100 — بوابة موضوعية
==================================================
لا تُحسب أي نقطة بسبب النية أو وجود كود فقط. الوصول إلى 100/100 يتطلب:

[ ] 0 unresolved critical failures
[ ] 0 recurring failures بلا RCA واضح
[ ] Canonical CI GREEN على latest main SHA
[ ] Typecheck GREEN
[ ] Lint/static GREEN
[ ] Production build GREEN
[ ] Contract tests GREEN
[ ] E2E/browser matrix GREEN عند انطباقه
[ ] SSR/CSR/hydration regressions مغلقة
[ ] Registry/Planner/Executor/Verifier contracts GREEN
[ ] Security gates GREEN
[ ] Error Memory محدثة وقابلة لإعادة الاستخدام
[ ] Auto-repair لا يكرر strategy فاشلة بلا Evidence جديد
[ ] Intractable protocol يعمل fail-closed
[ ] Exact-SHA evidence لكل release/repair مهم
[ ] Performance budgets GREEN أو deviations موثقة ومقبولة
[ ] i18n/routing/canonical/hreflang checks GREEN عند انطباقها
[ ] SEO Health Gate GREEN عند انطباقه
[ ] لا technical debt حرج معروف بلا task مقيد ومُرتب
[ ] task log متزامن مع الحالة الفعلية للمستودع

==================================================
13. EXECUTION ORDER — ترتيب العمل
==================================================
P0-A  → Canonical CI + Trust Baseline
P0-B  → Root-cause diagnostics + current RED failures
P0-C  → WebKit/SSR/CSR/hydration/routing root fixes عند وجودها
P0-D  → Self-healing/error-memory convergence
P0-E  → Security/contract verification
P0-F  → CI speed without coverage loss
P0-G  → Performance/local-first
P0-H  → SEO/i18n/UX release gates
P0-I  → Final exact-SHA certification

لا تنتقل إلى P0 التالي إذا كان السابق ما زال يحتوي failure حرجة، إلا إذا كانت المهمة اللاحقة لازمة مباشرة لتشخيص السابقة.

==================================================
14. AGENT EXECUTION RULE
==================================================
لا تغلق المهمة بعد أول إصلاح.
استمر تلقائيًا في:
inspect → repair → test → observe → diagnose → repair
حتى تصبح canonical path خضراء أو تصل الحالة إلى Intractable مع Teaching Packet موثق.

إذا ظهر فشل جديد أثناء التحقق، اعتبره مهمة جديدة مرتبطة بنفس المسار، لا سببًا لإنهاء المهمة.
إذا أصبح target SHA superseded، أغلق محاولة الإصلاح القديمة fail-closed وافتح دورة جديدة للـcurrent main SHA.

النتيجة المطلوبة النهائية:
نظام FLIXO موثوق، قابل للتوسع، قابل للتشخيص، self-healing بحدود، وآمن؛ والـ100/100 لا تُعلن إلا بعد Evidence فعلي.
```

# WP2 — SECURITY + OBSERVABILITY + ERROR INTELLIGENCE
**الأولوية: P0/P1 — حماية كل الحزم التالية.**

### الهدف
دمج الأمن والتشخيص وError Memory في طبقة واحدة حتى لا نكرر نفس أعمال الحماية والتتبع وإدارة الفشل عبر مراحل منفصلة.

### التنفيذ
- [ ] Security boundary للمدخلات والمعاملات والملفات.
- [ ] tool requirements وpermissions metadata-driven.
- [ ] منع path/file/network abuse وفق قدرات الأداة.
- [ ] traceId من الطلب حتى execution/verification.
- [ ] structured logs للأحداث الرئيسية.
- [ ] تصنيف الأخطاء: validation / execution / output / infrastructure / user-input.
- [ ] Error Memory قابلة لإعادة الاستخدام دون تحويل الخطأ السابق إلى صلاحية.
- [ ] حفظ RCA/evidence للحالات الفاشلة المهمة.
- [ ] recovery policies من Registry.
- [ ] حدود retries وreplans.
- [ ] diagnostics لا تكون مصدرًا ثانيًا للحقيقة.

## ACCEL-2 — تحسين Artifact Reuse
**الحالة: ACTIVE — يبدأ بعد ACCEL-1 مباشرة**

### الهدف
جعل build artifact ونتائج الاختبارات قابلة لإعادة الاستخدام دون إعادة build أو نسخ زائد.

### التنفيذ
- [ ] canonical build واحد لكل SHA.
- [ ] browser jobs تعتمد artifact البناء نفسه دون rebuild.
- [ ] إزالة أي download/upload غير ضروري بين مراحل workflow.
- [ ] تثبيت artifact identity بالـSHA والـfingerprint.
- [ ] تجميع النتائج في aggregation artifact واحد عند الإمكان بدل تكرار نفس الملفات.
- [ ] التأكد أن `certify` يستهلك artifacts ولا يعيد إنتاجها.

### بوابة ACCEL-2
لا يوجد rebuild لنفس SHA + artifact identity موثقة + certification consumption-only + CI GREEN.

## ACCEL-3 — تقليل Artifact Upload Overhead
**الحالة: ACTIVE — يبدأ بالتوازي مع ACCEL-2 عندما لا يغيّر correctness**

### الهدف
تقليل وقت وحجم رفع الأدلة من 15 browser jobs دون فقد evidence اللازمة للتشخيص أو certification.

### التنفيذ
- [ ] حصر الملفات التي يحتاجها certification فعلًا.
- [ ] فصل evidence الحرجة عن diagnostics الكبيرة.
- [ ] رفع evidence minimal لكل shard فقط.
- [ ] الاحتفاظ بالـtrace/video/screenshot عند الفشل أو عند الحاجة التشخيصية، لا كحمولة ثابتة لكل job.
- [ ] ضغط/تقليل الملفات النصية والنتائج المكررة قبل الرفع.
- [ ] منع رفع نفس التقرير من أكثر من shard.
- [ ] التحقق أن كل failure ما زال قابلاً لإعادة التشخيص بعد التقليل.

### بوابة ACCEL-3
Artifact payload أصغر + certification لا يفقد أي evidence مطلوبة + failure diagnostics قابلة للاستخدام + CI GREEN.
