# مشاريع التطوير — FLIXO-AI-TOOLS

> الخطة المرجعية لتنفيذ التطوير المعماري والتوسع بأمان، مع Evidence-First وPR مستقل وCI قبل الدمج.

## الوضع الحالي
- 20/20 أداة من القائمة الأصلية مكتملة.
- كل أداة تُضاف وتُختبر وتُدمج منفردة.
- Vercel ليس حكمًا على صلاحية الكود.
- لا تبدأ إعادة الهيكلة الكبيرة قبل تثبيت `main` وCI على SHA محدد.

## المراحل

### 1. Baseline
تسجيل SHA لـ`main`، حالة CI، PRs المفتوحة، والملفات الحساسة.

ملفات مرجعية لاحقة:
```text
docs/ARCHITECTURE-BASELINE.md
docs/TOOL-CONTRACT.md
docs/PERFORMANCE-BUDGET.md
```

بوابة النجاح:
```text
BASE SHA known
CI state known
Rollback point known
Open PR state known
```

### 2. Tool Contract
المبدأ:
```text
Registry = metadata
Router   = routing
Tool     = implementation
```
توحيد metadata دون إعادة بناء الـRouter كاملًا.

### 3. Code Splitting Proof
إثبات أن الـinitial bundle لا يحمل أكواد الأدوات الثقيلة غير المطلوبة، مع قياس Initial JS/CSS وTool Chunks وعزل اللغات وعدم تكرار القواميس.

### 4. Web Workers
استخدام Workers فقط للعمليات الثقيلة مثل PDF/Image/OCR/AI/Large Compression، مع timeout وAbort وcleanup وerror propagation وTransferable Objects.

### 5. Safe Cache
طبقات:
```text
Memory Cache
↓
IndexedDB metadata/cache
↓
Explicit File Cache عند الحاجة فقط
```
مع TTL وحدود حجم/إدخالات وcleanup وfallback، وعدم تخزين النتائج الحساسة تلقائيًا.

### 6. Smart Loading
التدرج:
```text
route preload
→ hover/focus preload
→ next-tool prediction
→ behavior-based prediction
```
بحد مبدئي 1–2 chunks، ومنع preload الشامل.

### 7. Search
البدء بـRegistry ثم normalized index وexact match وkeyword/category filtering. تقييم Fuse أو محرك مستقل فقط بعد نمو حقيقي إلى نحو 100 أداة.

### 8. Performance Observability
قياس LCP وINP وCLS وLong Tasks وInitial JS وTool Load وWorker Time وBuild/Verify/E2E وMemory. المراقبة تقيس فقط ولا تعبث بالـDOM أو تحمل الموارد تلقائيًا.

### 9. Quality Gates
```text
npm run check
npm run verify
```
والمسار لكل تغيير:
```text
Diff Review
→ TypeScript
→ ESLint
→ Contract
→ Targeted Test
→ Output Test
→ Build
→ Full Matrix
→ Security
→ Exact SHA Verification
→ Merge
```

### 10. Tool Template
الشكل المقترح:
```text
src/tools/<tool>/
├── index.tsx
├── engine.ts
├── types.ts
└── tests/

src/routes/<tool>.tsx
tests/<tool>.contract.spec.ts
```
القاعدة: PR واحد = أداة واحدة ما لم يوجد سبب هندسي مثبت.

### 11. Expansion
التوسع:
```text
20 → 30 → 50 → 75 → 100+
```
كل أداة تمر بنفس بوابة الجودة.

## المعمارية المستهدفة
```text
FLIXO
├── Registry
├── Router
└── Tool
    ├── UI
    ├── Engine
    └── Worker (عند الحاجة)
        ↓
    Contracts
        ↓
    Tests + CI
        ↓
      main
```

## ما لا ننفذه مبكرًا
- Hot update للمكونات داخل build أثناء التشغيل.
- Analytics إلزامية أو إرسال تلقائي افتراضي.
- Predictive preload واسع.
- Generic ToolPageGenerator قبل إثبات الحاجة.

## Rollback
لكل PR:
```text
Before SHA
After SHA
Changed Files
Expected Behavior
Validation Evidence
Rollback Method
```
ويفضل `Revert Merge Commit` بدل إصلاح يدوي فوق إصلاح.

## Vercel
```text
CODE_FAILURE
EXTERNAL_DEPLOYMENT_FAILURE
```
إذا كانت بوابات الكود GREEN وVercel متوقفًا خارجيًا:
```text
CODE VALID
DEPLOYMENT UNVERIFIED
```

## الأداء
ننشئ Baseline فعليًا ثم نقارن BEFORE/AFTER بدل أرقام وهمية.

المقاييس: Initial JS/CSS، Tool Chunk Isolation، LCP، INP، CLS، Build Time، Verify Duration، E2E Duration، Memory.

## قواعد السلامة
1. `main` مصدر الحقيقة الإنتاجية.
2. لا تعديل مباشر على `main`.
3. كل تغيير عبر PR.
4. كل أداة منفردة.
5. لا dependency جديدة بلا حاجة مثبتة.
6. لا refactor مع feature غير مرتبطة في PR واحد.
7. لا حذف تاريخي لمجرد التبسيط.
8. لا merge قبل إثبات SHA المحدد.
9. لا نستخدم Vercel كبديل لـCI.
10. النجاح يُقاس بالأدلة.
11. لا abstraction قبل الحاجة الفعلية.
12. لا نرفع التعقيد أسرع من نمو الأدوات.
