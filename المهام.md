## TASK AGENT — OWNER OF THIS FILE

`المهام.md` هو المصدر الوحيد لحالة المهام ونطاقها وترتيبها. **Task Agent** مسؤول عن قيادة دورة المهمة وتجهيز حزمة تنفيذ دقيقة، بينما الوكيل التنفيذي المشرف يملك قرار التطبيق والاختبار والإغلاق.

### مسؤوليات Task Agent
- قراءة `PROJECTS.md` ثم `المهام.md` ثم العقود والسياسات ذات الصلة قبل أي تخطيط.
- اختيار المهمة المفتوحة الأعلى أولوية فقط بعد فحص الاعتماديات والحواجز.
- فهم الهدف، النطاق، القيود، العقود، الأدلة، الاختبارات، ومخاطر المهمة.
- فحص baseline SHA والحالة الفعلية للمستودع قبل إعداد أي تغيير.
- إعادة استخدام البنية والعقود الموجودة قبل إنشاء أي مسار جديد.
- توزيع العمل ذهنيًا على الأدوار المتخصصة: Planner / Inspector / Implementer / Tester / Verifier / Learner.
- إعداد الكود والاختبارات والملفات المطلوبة للمهمة فقط.
- إنتاج **Prepared Changes / Patch Plan** دقيقًا وقابلًا للتطبيق والمراجعة.
- ربط كل حزمة بالمهمة والـbaseline SHA والعقود والأدلة المطلوبة.
- تسجيل blockers والافتراضات وعدم اليقين بدل تخمينها.
- تسليم العمل للوكيل التنفيذي المشرف مع حالة واضحة: `READY` أو `PREPARED_BLOCKED`.

### ممنوعات Task Agent
- ممنوع `git commit`.
- ممنوع `git push`.
- ممنوع إنشاء/دمج PR كإثبات تنفيذ.
- ممنوع تعديل `main` مباشرة كجزء من إعداد المهمة.
- ممنوع إعلان `CLOSED / VERIFIED` أو `GREEN`.
- ممنوع تجاوز `ZERO-FALSE-GREEN TASK RULE`.
- ممنوع توسيع النطاق تلقائيًا أو اختراع متطلبات.
- ممنوع استبدال عقد قائم بعقد جديد لمجرد سهولة التنفيذ.
- ممنوع اعتبار إعداد الكود تنفيذًا للمهمة.

## MULTI-AGENT EXECUTION SYSTEM — v1

هذه البوابة تنظم مجموعة الوكلاء كمنظومة واحدة، وليس كوكلاء مستقلين يتنافسون على نفس المصدر.

### الأدوار الرسمية

| الدور | الوظيفة | ممنوعاته |
|---|---|---|
| ORCHESTRATOR | يحدد الأولوية، يوزع العمل، يحسم التعارضات، ويقرر الانتقال بين المراحل | لا يتجاوز الأدلة أو الحواجز |
| TASK AGENT | يفهم `المهام.md` ويحوّل المهمة إلى حزمة تنفيذ قابلة للتطبيق | لا يطبق/يعمل commit/push |
| INSPECTOR | يفحص الكود والعقود والتاريخ ويحدد الجذر والنطاق المتأثر | لا يغير المصدر |
| PLANNER | يصمم أصغر خطة كاملة قابلة للتحقق | لا يوسع النطاق |
| IMPLEMENTER | يطبق التغييرات المصرح بها فقط على isolated worktree/branch | لا يغلق المهمة بنفسه |
| TESTER | يعيد إنتاج المشكلة ويشغل targeted regression ثم الاختبارات المطلوبة | لا يتجاوز فشل الاختبار |
| VERIFIER | يتحقق من SHA، diff، invariants، الأدلة، وعدم وجود false-green | لا يخفف شروط الإغلاق |
| LEARNER | يسجل RCA، سبب النجاح/الفشل، prevention rule، وإشارات التكرار | لا يغير العقد دون مراجعة |

```text
  ↓

  ↓

```

### قواعد التنسيق بين الوكلاء
- **Single source of truth:** `المهام.md` + `PROJECTS.md` + العقود المعتمدة.
- **Single writer per stage:** لا يسمح لوكيلين بتعديل نفس المصدر في المرحلة نفسها.
- **Immutable handoff:** كل تسليم يحمل `taskId + baselineSha + contractVersion + scope + evidenceRequirements`.
- **No stale work:** إذا تغير baseline SHA، تُرفض الحزمة القديمة ويجب إعادة التحضير.
- **Bounded scope:** كل تنفيذ يجب أن يثبت الملفات المتأثرة قبل التطبيق.
- **Fail closed:** أي غموض جوهري، تعارض عقد، أو فشل proof يحول الحالة إلى `BLOCKED` أو `ROLLBACK`.
- **Evidence first:** لا تعتمد النتيجة على الرسائل أو النوايا؛ تعتمد على artifacts وcommands وSHA قابلين للتحقق.
- **No duplicate repair:** إذا كان هناك إصلاح سابق لنفس fingerprint، يسترجع من الذاكرة أولًا ويُعاد التحقق منه قبل إنشاء إصلاح جديد.
- **Parallelism by isolation:** الأعمال المستقلة فقط يمكن تنفيذها بالتوازي، وكل عمل يملك baseline وworkspace مستقلين.
- **Integration gate:** لا يتم دمج مخرجات وكلاء متعددة قبل فحص التعارضات، حدود النطاق، والاختبارات المشتركة.

### حالات المهمة الموحدة

```text
QUEUED
→ UNDERSTANDING
→ INSPECTED
→ PLANNED
→ PREPARED
→ READY_FOR_EXECUTION
→ EXECUTING
→ TARGETED_VERIFIED
→ REGRESSION_VERIFIED

```

حالات الفشل:

```text

```

ولا يجوز الانتقال من حالة إلى أخرى دون الدليل المناسب لكل انتقال.

### حزمة التسليم الإلزامية
يجب أن تحتوي كل handoff على:
1. `taskId`
2. `baselineSha`
3. `contractVersion`
4. فهم المشكلة والهدف
5. scope وحدود الملفات
6. الملفات التي يجب إنشاؤها/تعديلها
7. الكود الجاهز للتطبيق
8. الاختبارات والأوامر المطلوبة
9. المخاطر والافتراضات
10. شروط الإغلاق والأدلة المطلوبة
11. `status = READY | PREPARED_BLOCKED`
12. digest للحزمة عند توفره

### معيار الكفاءة الأعلى
الهدف ليس زيادة عدد الوكلاء؛ الهدف هو تقليل:
- إعادة العمل.
- التعديلات غير الضرورية.
- زمن الوصول إلى السبب الجذري.
- false-green.
- إصلاحات التكرار لنفس العطل.
- تعارضات الوكلاء.

وزيادة:
- دقة التشخيص.
- إعادة استخدام المعرفة التاريخية.
- حجم الأدلة القابلة للتحقق.
- قابلية إعادة الإنتاج.
- سرعة regression بعد الإصلاح.
- وضوح handoff.
- سلامة rollback.

## ZERO-FALSE-GREEN TASK RULE

A task may be marked `CLOSED / VERIFIED` only when all applicable conditions are proven on fresh evidence:

`MERGED TO MAIN ∧ EXACT MAIN SHA CONFIRMED ∧ REQUIRED CI / CERTIFICATION PASS ∧ TARGETED REGRESSION PASS ∧ INVARIANT PROOF ∧ CLOSURE EVIDENCE ∧ PROJECTS.md CLOSED HISTORY UPDATED`

A stale SHA, partial run, skipped required engine, provider-bypassed result, or inferred success does not satisfy closure.

`حذف المهمة قبل اكتمال أي شرط = PROTOCOL VIOLATION`

## PERFORMANCE-ENGINE-001 — طبقة أداء موحدة لمحرك معالجة الصور

STATUS = PLANNED
PRIORITY = P1
SCOPE = بناء Performance Layer موحدة لكل عمليات معالجة الصور الحالية والجديدة، بحيث تستخدم الأدوات مسارًا مشتركًا عالي الكفاءة بدل تكرار decode/preprocess/process/encode داخل كل أداة.
PRODUCT = AI Image Editing Agent + Manual Image Editing Catalog
GOAL = تقليل زمن التنفيذ، منع تجميد Main Thread، خفض استهلاك الذاكرة، تقليل إعادة المعالجة، وتحسين سرعة الاستجابة دون التضحية بجودة الصورة أو صحة المخرجات أو الأمان.

### PERFORMANCE ARCHITECTURE

الخط القياسي:

Input
→ Decode
→ Preprocess
→ Operation
→ CPU/GPU/WASM execution
→ Verification
→ Encode
→ Output

المبدأ:

ONE IMAGE ENGINE + ONE SHARED PIPELINE + TOOL-SPECIFIC OPERATION ADAPTERS

لا تنشئ كل أداة pipeline مستقلة إذا كان المحرك المشترك قادرًا على استيعابها.

### EXECUTION BACKENDS

BACKENDS = CPU | WEB_WORKER | OFFSCREEN_CANVAS | GPU | WASM

RULES =
- نقل العمليات الثقيلة خارج Main Thread متى كان ذلك مناسبًا.
- استخدام Web Workers للعمليات الحسابية/البكسلية الثقيلة.
- استخدام OffscreenCanvas عندما يدعم المسار والمتصفح ذلك.
- استخدام GPU/WebGL/WebGPU فقط للعمليات التي تستفيد فعليًا منه.
- CPU fallback إلزامي عندما لا يتوفر backend متقدم أو عندما تكون كلفة النقل أعلى من فائدته.
- WASM يستخدم للعمليات الثقيلة المناسبة، مع lazy loading وعدم تحميله قبل الحاجة.
- لا يجوز أن يؤدي اختيار backend إلى تغيير النتيجة المطلوبة دون proof لجودة المخرجات.

### IMAGE PIPELINE CONTRACT

### DECODE / PREPROCESS

REQUIREMENTS =
- تقييم createImageBitmap() كمسار decode أساسي عندما يكون مناسبًا.
- تجنب نسخ الصور الكبيرة دون ضرورة.
- استخراج metadata والدقة مرة واحدة وإعادة استخدامها.
- تحديد working resolution قبل المعالجة.
- دعم full-resolution processing فقط عندما تتطلبه العملية أو Apply/Export.
- preview resolution منفصل عن export resolution.

### PREVIEW PIPELINE

أثناء التفاعل مع:
- Intensity
- Brightness
- Contrast
- Color
- Filters
- عمليات مشابهة منخفضة التكلفة

يستخدم المحرك preview منخفض الدقة/منخفض التكلفة، ثم ينفذ full-resolution عند Apply.

RULE = slider interaction MUST NOT trigger full-resolution encode/decode لكل حركة.

### REGION / INCREMENTAL PROCESSING

إذا كانت العملية محصورة بمنطقة من الصورة:
- حدد affected region.
- لا تعالج كامل الصورة إذا كان backend/operation يسمح بالمعالجة الجزئية.
- حافظ على coordinates والتحويلات بدقة.
- verification يجب أن يثبت أن المنطقة غير المتأثرة لم تتغير إلا عندما تكون العملية بطبيعتها global.

### PIPELINE FUSION

يجب دمج العمليات المتوافقة قبل encode/decode:

BAD:
decode → filter → encode → decode → resize → encode

TARGET:
decode → filter + resize → verify → encode

RULES =
- لا encode/decode وسيط إلا لسبب مثبت.
- ترتيب العمليات محفوظ دلاليًا؛ fusion ممنوع إذا كان سيغير النتيجة.
- كل optimization يجب أن يثبت equivalence أو فرقًا مقبولًا محددًا حسب نوع العملية.

### CACHE

CACHE LEVELS =
- decoded image metadata
- reusable decode/bitmap representation
- preview results
- deterministic operation results
- compatible pipeline intermediates

CACHE KEY يجب أن يرتبط على الأقل بـ:
image/content identity + operation + normalized parameters + relevant resolution + engine/version

RULES =
- لا cache عبر مستخدمين أو جلسات بطريقة تكشف بيانات خاصة.
- invalidation إلزامي عند تغير المدخل أو المعلمات أو engine version.
- memory pressure يجب أن يؤدي إلى eviction آمن.
- cache hit لا يعفي من verification عندما تكون verification مطلوبة.

### CANCELLATION / CONCURRENCY

REQUIREMENTS =
- كل execution قابل للإلغاء.
- طلب جديد يلغي أو يستبدل العملية السابقة عندما لا تعود النتيجة مطلوبة.
- stale worker result ممنوع من الكتابة فوق currentArtifact.
- استخدام execution/request generation أو equivalent ordering guard.
- Worker pool محدود حسب CPU/Memory والقياسات الفعلية.
- لا unbounded parallelism.
- لا duplicate execution نتيجة slider/input churn.

SAFE STATES =
CANCELLED | SUPERSEDED | COMPLETED | FAILED | VERIFIED

### MEMORY MANAGEMENT

REQUIREMENTS =

- revokeObjectURL() للـObject URLs التي لم تعد مطلوبة.
- تجنب الاحتفاظ بنسخ full-resolution متعددة بلا ضرورة.
- وضع حدود آمنة للعمل على الصور الكبيرة.
- التعامل مع allocation failure/fallback دون crash أو false success.
- قياس peak memory في benchmark.
- لا يحتفظ cache بالصور الحساسة بعد انتهاء lifecycle المحدد.

- verification بعد encode يجب أن يثبت قابلية القراءة وصحة format وأبعاد المخرج والبيانات الأساسية المطلوبة.
- لا يتحول optimization إلى loss غير معلن.

### LAZY LOADING

RULES =

- code splitting حسب capability/backend.
- عدم تحميل WASM/GPU modules في المسار الأولي دون سبب.
- لا تضحي lazy loading بزمن أول استخدام دون قياس؛ يجب قياس cold start مقابل warm start.

## FINAL-QA-001 — وكيل المراجعة والإصلاح النهائي للصور

STATUS = PLANNED
PRIORITY = P1
GOAL = منع إخراج أي صورة نهائية قبل اجتياز فحص تقني وبصري ودلالي قابل للإثبات، مع إصلاح آمن محدود ثم إعادة التحقق عند وجود عيب قابل للإصلاح.

### ARCHITECTURAL POSITION
المسار الإلزامي:
Understand → Plan → Execute → Inspect → Repair → Verify → Deliver

FINAL-QA-001 لا يستبدل Verification Layer ولا Execution Layer؛ يعمل عبر Canonical Editing Session وUnified Capability Registry وPERFORMANCE-ENGINE-001.

### OUTCOME CONTRACT
- PASS = جميع الفحوص الإلزامية اجتازت الحدود المعتمدة.
- REPAIR = عيب قابل للإصلاح الآمن؛ ينفذ إصلاحًا مسموحًا ثم يعيد الفحص.
- BLOCK = فشل غير قابل للإصلاح الآمن، أو نقص evidence، أو تجاوز حدود الإصلاح.
UNKNOWN/UNVERIFIED لا يتحول إلى PASS.

### INSPECTION LAYERS
1. Technical: dimensions, format, encoding, alpha, metadata policy, integrity, readability.
2. Deterministic Difference: changed-region analysis, unexpected changes, pixel/dimension invariants, original/result consistency.
3. Visual Quality: artifacts, noise, halos, melted/smeared regions, broken edges, unintended blur, lighting/color anomalies, composition defects.
4. Semantic/Intent: requested edit completed, protected subject preserved, forbidden/unrequested changes detected, crop/composition respected.
5. Fine Detail: face/object/edge preservation, hair/transparent boundaries, text/logo integrity when relevant.

### DETERMINISTIC + VISUAL DUAL GATE
كل نتيجة تمر عبر:
Deterministic QA + Visual QA Agent → Verification Gate

لا يكفي نجاح الوكيل البصري وحده، ولا يكفي نجاح فحص الملف وحده عندما تتطلب المهمة جودة/نية بصرية. Visual QA disagreement يتحول إلى REPAIR أو BLOCK حسب policy.

### REPAIR BOUNDARY
الإصلاح يجب أن يكون عبر Capability Registry فقط، محدد النطاق، قابلًا للإلغاء، محدود الدورات، ومرتبطًا بـrequestId وartifact/version.
لا يستطيع QA تغيير طلب المستخدم أو تعطيل Verification Gate أو security/policy/promotion rules.
إذا لم يوجد repair capability موثوق = BLOCK.

### RE-CHECK LOOP
MAX_QA_REPAIR_CYCLES حد صريح في contract.
كل دورة تسجل requestId، artifactId/version، findings، repair capability، parameters، before/after evidence، verification result، remaining findings.
PASS → Deliver؛ BLOCK → Stop؛ تجاوز الحد → BLOCK.

### EVIDENCE CHAIN
requestId → input artifact → normalized intent → plan → execution artifact → deterministic QA → visual QA → findings → repairs → re-checks → final verification → final artifact.
كل PASS يملك evidence قابلًا لإعادة الفحص.

### ANTI-HALLUCINATION / JUDGE SAFETY
Visual QA لا يدعي رؤية ما لم يُحلل، ولا يحول عدم اليقين إلى PASS، ولا يخترع تغييرات، ولا يعتمد على وصف نصي بدل artifact الفعلي، ولا يغير الصورة بلا finding مرتبط بالطلب أو quality policy.
confidence/uncertainty تسجل؛ النتيجة غير الحاسمة تبقى UNVERIFIED وتصبح BLOCK عند التسليم إن لم يوجد دليل كافٍ.

### PERFORMANCE INTEGRATION
cheap deterministic checks أولًا، targeted visual checks ثانيًا، expensive inspection عند الحاجة.
Preview QA وFinal QA لهما budgets منفصلة.
تقاس: qa_decode_ms, qa_deterministic_ms, qa_visual_ms, qa_total_ms, qa_peak_memory_mb, qa_main_thread_block_ms, qa_repair_cycles, qa_repair_time_ms.

### SECURITY / PRIVACY
الصورة لا تغادر حدود السياسة دون تصريح. أي provider خارجي يجب أن يكون معلنًا ومسموحًا. لا إرسال تلقائي لصور حساسة. metadata/privacy rules تطبق على artifacts وevidence. QA لا يملك صلاحية تغيير security/privacy policy.

### FAILURE TAXONOMY
استخدم taxonomy الموحد: INTENT_FAILURE, CONTEXT_FAILURE, EXECUTION_FAILURE, INSPECTION_FAILURE, VERIFICATION_FAILURE, POLICY_FAILURE, PROVIDER_FAILURE, MEMORY_FAILURE, PERFORMANCE_FAILURE, REPAIR_FAILURE.

### TEST CONTRACT
اختبار PASS، REPAIR، BLOCK، missing evidence، unresolved disagreement، repair limit، unauthorized capability، policy bypass، artifact/version confusion، original preservation، requested-change preservation، unintended-change detection، technical integrity، representative artifacts، text/logo/face/edge cases عند انطباقها، mobile/desktop، performance، security/privacy.

### ACCEPTANCE
لا يغلق FINAL-QA-001 إلا بعد canonical contract، deterministic checks، visual inspection، intent compliance، PASS/REPAIR/BLOCK، bounded repair loop، exact evidence chain، fail-closed unknown، security/privacy، performance measurement، targeted/integration tests، static/typecheck/build، required CI/certification، exact SHA، clean worktree.

### DEPENDENCIES
PERFORMANCE-ENGINE-001; Unified Capability Registry; Canonical Editing Session; Verification Layer; Agent Reasoning/Planning; Undo/Redo + History; Error taxonomy/evidence chain.

### OUT_OF_SCOPE
