# FLIXO-AI-TOOLS — بوابة المهام التنفيذية

> **الإصدار:** TASK-GATE v2.0
> **الحالة:** ACTIVE / REQUIRED AGENT GATE
> **الغرض:** حفظ قائمة العمل المفتوحة وخطة التنفيذ الكاملة بحيث يمكن لأي وكيل استئناف العمل من الحالة الفعلية دون فقدان المهام أو اختراع مهام جديدة.
> **مصدر الحقيقة التشغيلي:** `main` + `PROJECTS.md` + هذه الوثيقة + العقود الحاكمة + Fresh Exact-SHA Evidence.
> **ممنوع اعتبار أي SHA أو Evidence تاريخي دليلًا للحالة الحالية دون إعادة التحقق.**

## 0. قاعدة الدخول الإلزامية

قبل أي قراءة للكود أو تعديل أو اختبار أو تشغيل CI يجب على كل وكيل تنفيذ التسلسل التالي:

```text
PROJECTS.md
→ المهام.md
→ AGENTS.md
→ INGEST HANDOFF
→ RESOLVE EXACT main SHA
→ IDENTIFY ACTIVE TASK
→ READ AUTHORITATIVE CONTRACT
→ RCA / SCOPE LOCK
→ EXECUTE MINIMUM PROVEN CHANGE
→ TARGETED REGRESSION
→ AFFECTED CONTRACT GRAPH
→ EXACT-SHA PROOF
→ UPDATE PROJECTS.md + المهام.md
→ HANDOFF / LOGOUT
```

عدم قراءة `المهام.md` يعني عدم امتلاك نطاق تنفيذ معتمد.

## 1. مبادئ الالتزام الصارمة

1. `main` هو مصدر الحقيقة الحالي.
2. `ACTIVE` فقط هو التنفيذ المصرح به مباشرة.
3. `LOCKED` يعني dependency-gated وليس منسيًا.
4. `CANDIDATE ≠ ACTIVE`.
5. `DEFER ≠ forgotten`.
6. `BLOCKED ≠ STOP`.
7. `UNKNOWN ≠ PASS`.
8. `INCOMPLETE ≠ SUCCESS`.
9. لا Green من CI جزئي، أو فرع غير مدمج، أو SHA مختلف، أو Evidence قديم، أو provider bypass.
10. لا تعطيل اختبارات، ولا تخفيف assertions، ولا حذف coverage، ولا تحويل failure إلى warning لإخفاء defect.
11. لا LLM-direct production execution ولا تجاوز authorization/policy/approval/evidence.
12. لا duplicate registry / validator / truth store / execution owner بلا حاجة مثبتة.
13. كل defect يبدأ بـRCA واضح، وكل RCA يغلق فقط بالسبب الجذري + regression + contract proof + fresh exact-SHA evidence.
14. عند تحرك `main` يجب إعادة حل SHA قبل الاستمرار.
15. لا تُضاف مهمة جديدة إلى القائمة إلا بمصدر حاكم، owner، invariant، exit criteria، وnext deterministic action.

## 2. بروتوكول حفظ المهام وعدم فقدانها

هذه الوثيقة هي **Open Task Queue**. لا يُفترض أن يكون لها حالة فارغة بسبب حذف معلومات العمل.

كل مهمة مفتوحة يجب أن تحمل على الأقل:

```text
TASK ID
TITLE
STATUS
PRIORITY
OWNER / SCOPE
DEPENDENCIES
AUTHORITATIVE CONTRACT
ENTRY SHA
CURRENT HEAD SHA
RCA / INVARIANT
TARGETED TEST
EXIT CRITERIA
CURRENT EVIDENCE
NEXT DETERMINISTIC ACTION
BLOCKER
```

وعند كل انتقال مهم:

```text
ACTIVE → IMPLEMENTED / VERIFICATION PENDING
IMPLEMENTED / VERIFICATION PENDING → CLOSED / STABLE
ACTIVE ↔ BLOCKED
CANDIDATE → ACTIVE
CANDIDATE → DEFER
```

يجب تحديث `PROJECTS.md` و`المهام.md` معًا في نفس عملية الحالة المنطقية. لا تعتمد استمرارية المهمة على Chat memory.

## 3. قاعدة الاستئناف بعد انقطاع الجلسة

عند بدء أي وكيل جديد:

```text
READ PROJECTS.md
→ READ المهام.md
→ READ AGENTS.md
→ INGEST predecessor handoff
→ RESOLVE current main SHA
→ MATCH task ID + dependency state
→ CONTINUE from last verified checkpoint
```

ممنوع إعادة استخدام:

```text
stale branch state
old PR state
old SHA
old CI
old browser evidence
old deployment evidence
chat-only assumptions
```

إذا تغير `main`، فإن `entrySha` القديم يبقى سجلًا تاريخيًا فقط ويجب إنشاء checkpoint جديد للـSHA الحالي.


## 6. خطة تنفيذ ADMIN-003 → ADMIN-008

### ADMIN-003 — Truth / Command / Security / Contract / Operations / Incident Centers

هدف الإغلاق:

```text
canonical read models
+ center-specific authorization
+ read-only behavior proof
+ traceable claims
+ current SHA proof
```

التنفيذ:

```text
Inspect current main
→ verify canonical centers adapter
→ verify capability matrix
→ negative authorization tests
→ read-only enforcement tests
→ static/build/browser affected graph
→ certification
→ update task state
```

### ADMIN-004 — Controlled Execution + Rollback

ممنوع الانتقال إليه قبل إثبات ADMIN-003.

المسار:

```text
Intent
→ deterministic command
→ authorization
→ policy
→ preview
→ approval when required
→ execution
→ verification
→ evidence
→ audit
→ rollback proof
```

الـMVP يبقى fail-closed؛ أي write غير مثبت لا يتحول إلى production mutation لمجرد توفر الواجهة.

### ADMIN-005 — Change / Approval / Incident

يوحد:

```text
PR / Commit / Change provenance
→ Risk
→ Required approval
→ Incident linkage
→ Verification
→ Rollback metadata
```

كل change يجب أن يرتبط بالعقد والـtests والـevidence الفعلية.

### ADMIN-006 — Truth Graph

لا يبدأ بناء الرسم البصري قبل ثبات مصادر البيانات.

العقد:

```text
Production
→ Deployment
→ Exact SHA
→ Contract
→ Check
→ Evidence
→ Verdict
```

أي node غير قابل للإسناد يصبح `UNKNOWN / UNAVAILABLE / STALE` وليس GREEN.

### ADMIN-007 — Controlled AI Assistant

يسمح للـAI بـ:

```text
summarize
correlate
explain
recommend deterministic action
navigate truth graph
```

ولا يسمح له بـ:

```text
invent evidence
self-certify GREEN
bypass authorization
bypass approval
execute arbitrary code
mutate production directly
grant capabilities to itself
```

### ADMIN-008 — Production Certification

الإغلاق النهائي يتطلب في candidate SHA واحد:

```text

+ clean worktree
+ required CI PASS
+ security proof
+ auth proof
+ persistence/read-back proof where required
+ browser proof
+ live production SHA proof
+ post-change verification
+ no stale evidence
+ no false-green path
```

## 7. المرشحون الآخرون

`BUILD-002`, `I18N-001`, `TEST-001`, `DEBT-001` تبقى `CANDIDATE` حتى يثبت defect أو قيمة تنفيذية حالية من fresh evidence.

لا يبدأ أي منها لمجرد وجود ملاحظة تاريخية.

## 8. التوسع إلى أدوات الصور والمونتاج

يوجد backlog وظيفي كبير سابقًا لأدوات تعديل الصور والمونتاج والتحسين وAI، لكنه **ليس ACTIVE** تلقائيًا. أي أداة جديدة يجب أن تدخل عبر نفس دورة:

```text
Idea
→ capability definition
→ Tool Contract
→ Registry
→ Implementation
→ Targeted Test
→ Output Proof
→ Build
→ Full Matrix as required
→ Exact SHA
→ Merge
→ Close
```

الحد التنظيمي:

```text
PR واحد = أداة واحدة
```

إلا إذا كان سبب جمع الأدوات في تغيير واحد مثبتًا ومقبولًا تعاقديًا.

لا يجوز تحويل قائمة الـ100+ أداة إلى تنفيذ دفعي غير مضبوط.

## 9. بروتوكول RCA الإلزامي

لكل failure:

```text
RCA-ID
trigger
→ propagation path
→ violated invariant
→ responsible source
→ observable symptom
```

الإصلاح المقبول:

```text
mechanism proven
→ causal source repaired
→ targeted regression passes
→ affected contract graph passes
→ fresh exact-SHA evidence proves closure
```

الممنوع:

```text
retry only
silent skip
allowlist
weaken assertion
change expected value to fit defect
remove test
move failure to another layer
```

## 10. RCA الحالي للـAction الأخير

### RCA-ID
`RCA-CD-PROD-IDENTITY-001`

### الحالة
`OPEN / REPAIR IMPLEMENTED / VERIFICATION PENDING`

### الحدث
في CD run `34791437240` على SHA:

`6a93798e232b43ba539ba1dfbe7fa1dcfedb560c`

نجح:

```text
promotion SHA proof
certified artifact download
artifact SHA verification
Vercel deployment
production aliasing
```

وفشل فقط:

```text
Production identity proof
reason=DEPLOYMENT_IDENTITY_MISMATCH
```

### السبب الجذري
كانت خطوة التحقق من deployment-specific URL شرطًا للتحكم في الوصول إلى canonical production proof:

```text
deployment URL probe FAIL
→ canonical production probe NOT EXECUTED
→ job FAIL
```

هذا خلط بين **diagnostic deployment evidence** و**authoritative canonical production evidence**.

### الإصلاح المطلوب
الـdeployment-specific probe أصبح diagnostic evidence فقط، بينما:

```text
canonical production HTML probe
AND
canonical production SHA probe
```

يجب أن ينفذا دائمًا بشكل مستقل.

يبقى الـfail-closed invariant محفوظًا:

```text
PASS ⇔ canonical SHA == promotion SHA ∧ canonical HTML == PASS
```

### دليل الإصلاح
تم إصلاح `.github/workflows/cd.yml` في commit:

`156660655b01d2924161815c1e85acdfe120a04d`

الحالة: **لم تُثبت بعد بــfresh CI/CD run على هذا التغيير**.

## 11. بروتوكول الحذف بعد التنفيذ

الهدف من الحذف هو تنظيف `Open Task Queue` فقط.

لا تحذف مهمة إلا إذا تحقق جميع الآتي:

```text
MERGED TO MAIN
∧
EXACT MAIN SHA CONFIRMED
∧
TARGETED TESTS PASS
∧
REQUIRED CI / CERTIFICATION PASS
∧
TASK INVARIANT PROVEN
∧
NO DEPENDENT REPAIR OPEN
∧
CLOSURE EVIDENCE RECORDED
∧
PROJECTS.md CLOSED HISTORY UPDATED
∧
NEXT TASK / DEPENDENCIES UPDATED
```

عند الحذف:

```text
1. remove from Open Task Queue
2. append closure record to PROJECTS.md / Closed History
3. preserve taskId, RCA, invariant, closure SHA, CI run, evidence, verdict
4. never reuse closed evidence for another SHA
5. new defect = new RCA/task identity
```

حذف المهمة قبل اكتمال الشروط = `PROTOCOL VIOLATION`.

## 12. الترقية بين الحالات

```text
CANDIDATE
  ↓ proven need
ACTIVE
  ↓ implementation
IMPLEMENTED / VERIFICATION PENDING
  ↓ exact proof
CLOSED / STABLE
```

`LOCKED` لا ينتقل إلى `ACTIVE` إلا بعد اكتمال dependency exit criteria.

`BLOCKED` لا يعني انتهاء المهمة؛ يعني حفظ blocker واستكمال العمل المستقل.

## 16. Definition of Done للمهمة

لا تُعتبر المهمة `CLOSED / STABLE` إلا عند تحقق:

```text
CORRECT BEHAVIOR
+ ROOT CAUSE CLOSED
+ CONTRACT PASS
+ TARGETED REGRESSION PASS
+ REQUIRED CI PASS
+ EXACT SHA MATCH
+ FRESH EVIDENCE
+ NO DEPENDENT REPAIR
+ PROJECT MAP UPDATED
```

## 17. تعريف GREEN

```text
GREEN
=
EXACT SHA
∧ CLEAN STATE
∧ REQUIRED TESTS PASS
∧ REQUIRED CERTIFICATION PASS
∧ VALID EVIDENCE
∧ ZERO INDEPENDENT RCA
```

أي حالة أقل من ذلك هي `NOT GREEN` مهما كان مظهر الواجهة أو نجاح جزء من الـpipeline.

## 18. بروتوكول التسليم بين الوكلاء

كل handoff يجب أن يذكر:

```text
taskId

entrySha

```

الوكيل التالي لا يعيد اكتشاف المهمة من الصفر إذا كان handoff صالحًا؛ يستأنفها من آخر exact verified checkpoint.

## 19. قاعدة التوقف الوحيدة المقبولة

لا يوجد `STOP` كحالة عمل طبيعية.

يمكن فقط الانتقال إلى:

```text
BLOCKED
```

مع تسجيل السبب والدليل والعمل المستقل التالي، أو:

```text
CLOSED / STABLE
```

بعد استيفاء Definition of Done.
